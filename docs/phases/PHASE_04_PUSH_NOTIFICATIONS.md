# PHASE 04 — Push Notifications

## Goal
Every publish from a followed, non-muted masjid reaches musallis' phones (Android and installed iOS) within about a minute, localized, audience-filtered, quota-limited, and opening the exact item on tap. The pipeline scales to 50,000 recipients per post, prunes dead subscriptions, and can be paused globally.

## Owner prerequisites
- No new accounts (jobs run on BullMQ + the VPS Redis). VAPID key pair generated by Claude Code locally; the owner puts the private key only into the **worker** env file on the staging VPS (public key into api-admin env and the client build). **The VAPID private key must be backed up by the owner** (password manager / offline copy) — losing it invalidates every subscription.
- Test phones: Android (Chrome) + iPhone (iOS 16.4+, app installed to Home Screen).

## Out of scope
Notification categories/preferences (rejected — DECISIONS #16). Scheduled posts.

## Tasks

### T4.1 — Push infrastructure
**Do:** `packages/api/src/push/` adapter over `web-push` (VAPID from env; TTL/urgency/topic headers; response classification), endpoint host allow-list validation (04 §6), `packages/api/src/jobs/queue.ts` (BullMQ queue definitions, typed job payloads validated with Zod on both enqueue and process, default attempts/backoff/timeouts, removal policies), enqueue-after-commit helper for the outbox, idempotency helper (Redis keys), worker bootstrap registering processors + job schedulers (Asia/Kolkata), mock push service for tests (records requests, can return 201/404/410/429/500).
**Acceptance:** [ ] Unit tests for response classification and header building. [ ] Subscription with non-allow-listed host rejected. [ ] An invalid job payload is rejected at enqueue and at process time.

### T4.2 — Musalli subscription UX
**Do:** Notifications onboarding page (A1 step 7) + soft-ask sheet after first follow (Android: any mode; iOS: installed app only) + Settings → Notifications (status: On / Off / Blocked / "Install app first" on iOS non-standalone, with fix-it instructions per platform) + per-masjid mute list. Subscribe on user tap only (`pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })`), `PUT /devices/me/push` (via `setDevicePush`, which also updates `push_active` on the device's follows in the same transaction); unsubscribe path; `pushsubscriptionchange` handling in SW + re-check on every app open (if permission granted but no/changed subscription → resubscribe). iOS: only offer inside standalone mode.
**Acceptance:** [ ] Permission denied → clear guidance, no repeated prompts. [ ] Re-subscribe logic unit-tested with mocked PushManager.

### T4.3 — Service worker push handling
**Do:** `push` event: parse JSON, validate with Zod (01 §5.3 payload), **always** `showNotification` (fallback generic text if invalid), options: `body`, `icon` (app icon), `badge` (monochrome), `tag` (item public id), `renotify: false`, `data: {url, masjidId, cv}`, `lang`, `dir` (rtl for ur). Set app badge (`navigator.setAppBadge`) with unseen count where supported. `notificationclick`: focus an existing client and `postMessage({navigate})`, else `openWindow(url)`; URL must be same-origin relative. Client receives messages → navigate + trigger version poll for that masjid. Item removed later → item screen shows "This content is no longer available".
**Acceptance:** [ ] SW unit tests (workbox-sw test harness or service-worker mock) for valid/invalid payloads and click routing. [ ] E2E (Chromium): trigger push via test hook to a real local subscription → notification shown (Playwright can assert via SW `getNotifications()`).

### T4.4 — Fan-out pipeline
**Do:** On publish (all item types incl. timing_update and future types): within the publish transaction insert the `notification_jobs` outbox document + increment quota usage (IST day, conditional update) atomically; after commit enqueue BullMQ `push-fanout` (job id = notification job id). Processors `push-fanout` and `push-send-batch` exactly per `01 §5.3` (keyset pagination on the `device_follows` fan-out index, audience filter: `everyone` → all; `brothers`/`sisters` → matching `audience_pref`; muted and `push_active:false` excluded; locale grouping; batch size 1,000; concurrency 50). Outbox sweeper job. Localized title/body built per locale (templates via ICU on server using the same renderer package as the client; free text as-is; title = masjid name in that locale's script if available). Handle 404/410 → `push_status='dead'` + follows `push_active=false`; retries via BullMQ backoff on 429/5xx with the Redis sent-set so no endpoint gets a duplicate; idempotent per (job, page, locale). Job counters and `completed` status; stuck-job detector (no progress 10 min → `failed` + alert).
**Acceptance:** [ ] Integration tests with mock push service + real Redis/BullMQ: correct recipients for each audience/mute/push-status combination; locale grouping; pruning; retry idempotency (a batch retried after partial success, and a duplicated fan-out enqueue, send nothing twice). [ ] Outbox: a job whose enqueue was lost (Redis flushed in the test) is picked up by the sweeper and delivered once. [ ] No HTTP route can trigger a job (route table test).

### T4.5 — Quotas & admin visibility

Super Admin can change per-masjid quota (already in C2) and sees push success rates in Stats.
**Acceptance:** [ ] Quota resets at IST midnight (clock-controlled test). [ ] UI counts match DB (integration).

**Acceptance:** [ ] Super Admin receives a test alert from a dev-only trigger on staging.

### T4.7 — Kill switch
**Do:** `app_settings.push_paused` (Super Admin Settings ★): fan-out and send-batch processors check it and stop (jobs stay `pending`/delayed, not lost); banner on Super Admin dashboard while paused; admins see "Notifications are temporarily paused".
**Acceptance:** [ ] Integration test: paused → zero sends; resume → pending jobs continue.

### T4.8 — Fan-out load test

**Acceptance:** [ ] 50k dispatched in < 3 min; no batch exceeds its processor timeout; worker stays within its container memory limit; results table in report.
