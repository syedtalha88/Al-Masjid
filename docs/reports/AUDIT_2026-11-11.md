> Requested by the owner. Scope: everything built so far (Phases 00 – 05 T5.5, branch `feat/phase-05` at `061830b`).
> Method: checks run against the code, config, CI and staging results on 11 Nov 2026 — each finding names its evidence.
> This is not legal advice and it is not an independent audit: the same tool that built the app checked it (see §7).

## 1. Verdict

**Not ready for production — and it is not supposed to be yet.** 5 of 10 phases are built. What is built is in good
shape: I found no critical or high-severity security hole in the finished parts. The gaps are almost all work that is
planned but not done, and the biggest ones are legal, not technical.

**You cannot go to production "blindly", now or later.** No audit can give that. What you can have is a short list of
conditions that must all be true on launch day — that list is §6.

## 2. What I checked and found good

**Secrets and dependencies**
- No secret files are in git: only `.env.example` is tracked; `.env*`, `*.pem`, `*.key` are ignored. CI scans the whole
  history with gitleaks on every push, and every commit locally.
- `pnpm audit`: 0 critical, 0 high. 2 moderate + 1 low (see M1) — all in build tools, none reachable by a user.
- CI also runs osv-scanner, Semgrep (OWASP Top 10 + project rules), CodeQL, hadolint, Trivy on configs and on the built
  images, and a nightly re-scan with a fresh vulnerability database.

**Code boundaries (grep over `apps/` and `packages/`)**
- Every HTTP route goes through `defineRoute()` — 125 routes, 0 raw `router.get/post` calls. So every route has input
  validation, auth and a declared cache policy.
- Every write route (POST / PUT / PATCH / DELETE) has a rate limit — 0 exceptions.
- The database driver is imported only inside `packages/db`. `systemScope` is used only by the worker and scripts.
- No `eval`, no `new Function`, no `dangerouslySetInnerHTML`, no `innerHTML =` in shipped code. 9 uses of `any` /
  `@ts-ignore` in the whole code base, 2 TODO comments.

**Browser and server hardening**
- Content Security Policy on both apps: `script-src 'self'` (plus Turnstile and WebAssembly on the musalli app only),
  `style-src 'self'`, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, Trusted Types enforced.
- HSTS (2 years), `nosniff`, `X-Frame-Options: DENY`, COOP, CORP, Referrer-Policy, a tight Permissions-Policy.
- Admin cookies use the `__Host-` prefix (Secure, no Domain, Path=/).
- Containers: distroless, non-root (`65532`), pinned by digest, `read_only`, `cap_drop: ALL`, `no-new-privileges`.
- Release images are deployed only from a verified release manifest; the origin accepts only Cloudflare's client
  certificate; the shipped image is checked in CI to contain no test hooks; client bundles are scanned for secrets.

**Privacy by design**
- Musallis have no account. Location never leaves the phone. Money never passes through us.
- Tenant isolation is tested: 48 "another masjid" test cases in the database and API suites; the policy matrix and
  MongoDB privilege tests run in CI; the staging privilege check passed (O39, 10 Nov 2026).

**Quality**
- Tests today: unit 1,618 across 10 packages; database integration 344; API integration 362; e2e on Pixel 7 and
  iPhone 14 with accessibility checks. Coverage gates: domain 100 %, db 95 %, shared 95 %, api 90 %.
- CI on `main` is green; CI for Phase 05 (`16367cf`) is green.

## 3. Blockers — must be done before any real masjid uses it

**B1. The legal features of Phase 08 are not built.** Evidence: `legal_orders` appears only in the database schema; no
moderation queue, no SLA timers, no retention job in `packages/api/src/jobs`. Missing:
- Report button and moderation queue with takedown (36-hour, 2-hour and 3-hour clocks).
- Grievance tracker with the 24-hour acknowledgement.
- Legal-orders register.
- Retention job (180-day preservation, then purge).
- Kill switches and the breach banner.

Without these you cannot meet the IT Rules due-diligence duties, and that is what protects you from liability for what
masjid admins post. **This is the main legal risk in the project.**

**B2. Legal texts are drafts.** Only `privacy.md` and `undertaking.md` exist in `packages/i18n/legal/en`, both
`status: draft`. Terms, content policy, grievance page and licenses page are not written. None has been seen by a lawyer.
The production build is designed to refuse drafts — keep that.

**B3. Every translation is a machine draft.** About 1,613 strings each in Hindi, Urdu and Telugu, 0 reviewed (O31).
Wrong wording in a money or legal text is a real risk.

**B4. No production environment.** Phase 09 is not started: no production server or database, no backup-and-restore
drill, no monitoring or alerting, no load test, no incident runbook (only `DEPLOY.md` exists).

**B5. Your own legal checklist is open** (`owner/LEGAL_THINGS_I_NEED_TO_DO_MYSELF.md`): decide the legal entity, hire an
IT-law lawyer, name the Grievance Officer and a backup, register the CERT-In contact, collect each masjid's
authorization letter and proof of UPI ownership.

**B6. Religious content.** The app ships with fake placeholders by design. A licensed, scholar-verified Content Library
(O32) must be imported before launch.

**B7. Unverified and unfinished phases.** Phases 03 and 04 still wait for your checks (O25, O26, O38). Phase 05 is half
built and its new code — UPI change-lock, campaigns, chanda — has **not had its security review yet** (planned at
T5.7). Phases 06 and 07 are not started.

## 4. Findings to fix (in order)

**High**

- **H1. Nightly check red since 23 Oct: Cloudflare does not cache the public API on staging (O23).** The origin sends
  the right headers; the cache rule in your Cloudflare dashboard is missing or wrong. Why it matters: 44 read routes
  have no rate limit of their own and count on that cache to absorb traffic. Fix: you correct the rule (O23); I add a
  default per-IP limit to every route so nothing depends on the CDN alone.
- **H2. A security exception expires on 15 Nov 2026 (F61).** Two `zlib1g` CVEs in the base image are ignored until then
  (`infra/trivy/mc-server.trivyignore.yaml`). After that date CI goes red. Fix: move to the patched base image this week.
- **H3. Admin alerts keep arriving after sign-out (F65).** Signing out one admin phone, or its session expiring, does
  not stop push alerts to that phone. It was due "before Phase 05's first real alert to admins" — that is now, because
  UPI change requests alert admins. Fix before Phase 05 goes to staging.
- **H4. The GitHub repository is public.** It holds no secrets, but it does publish the full security design and
  `owner/` notes with the staging host names, the SSH user name and the tunnel address. Decide on purpose: make it
  private, or move the `owner/` operational notes out. Check first what a private repository changes on your GitHub
  plan (environments and approvals for deploys).

**Medium**

- **M1. Three dependency advisories.** `glob` and `minimatch` (moderate), `deepmerge` (low), pulled in by the build
  tools (workbox, eslint, the Sentry bundler plugin). They process our own files, not user input. Update when fixes
  land; Renovate will propose it.
- **M2. No error monitoring.** Sentry (O6) is optional and not set up. In production you would not know that users hit
  errors. Make it required before the pilot.
- **M3. `main` has no branch protection** (your choice, #150). Acceptable for one developer because production deploys
  need manual approval — but turn it on before a second person gets write access.
- **M4. Single points of failure.** One VPS runs the APIs, the worker and Redis. At 200 masjids that is fine, and the
  musalli app keeps showing timings offline, but an outage stops publishing and push. Needed before launch: tested
  backups, a written restore procedure, an uptime alert.
- **M5. One person holds everything.** Register a second Super Admin passkey on another device, and name a backup
  person for grievances — the legal clocks (3 hours for a court order) do not stop when you are asleep or travelling.
- **M6. Turnstile switch-over (O8) is still open** on staging.

**Low**

- **L1.** iPhone is tested only in CI (WebKit does not run reliably on this PC). Keep doing your real-iPhone checks.
- **L2.** Known push limits already tracked: F62 (a timed-out batch can cause one duplicate buzz), F63 (`Retry-After`
  not honoured), F64 (Pause takes effect per batch), F60 (`web-push` 4.x upgrade).
- **L3.** The repository has no LICENSE file. With a public repo that means "all rights reserved" — fine, but say so
  on purpose.

## 5. Scale

200 masjids × 50 users is about 10,000 devices. The design target in `01_ARCHITECTURE.md` is 1,000 masjids and
2,00,000 devices, so there is a wide margin. Not yet proven: the load and push fan-out tests are Phase 09 (T9.2); the
script exists (`scripts/load/push-fanout.ts`) but has not been run against a production-size setup.

## 6. Launch conditions — all must be true

1. Phases 05 – 09 finished, each verified by you on staging.
2. Phase 08 legal features live and tried once end to end (a test report, a test grievance, a test takedown).
3. Lawyer-approved privacy policy, terms, content policy, undertaking and grievance page; DRAFT banners gone.
4. Human-reviewed Hindi, Urdu and Telugu — legal and money texts first.
5. H1 – H4 closed; no open HIGH or MEDIUM finding from the security reviewer.
6. **An independent penetration test** by a person or firm that did not build the app, and its findings fixed.
7. Production on Atlas M10 with continuous backup, and one restore drill done.
8. Monitoring, alerts and an incident runbook with the CERT-In contact (6-hour reporting duty).
9. Grievance Officer and a backup named and shown in the app; second Super Admin passkey registered.
10. Verified Content Library imported.
11. Paperwork for every pilot masjid (authorization letter, UPI proof, phone confirmation).
12. A small pilot (3 – 5 masjids) for a few weeks before opening to 100+.

## 7. Limits of this audit

- Claude Code wrote the code and wrote this audit. The same blind spots can apply to both. Items 3 and 6 above exist
  for that reason — do not skip them.
- I did not log in to the server, Cloudflare, Atlas or Cloudinary. Their settings were checked only through the
  nightly tests and your earlier reports.
- I did not re-read every line. The checks were targeted: boundaries, headers, containers, dependencies, test and CI
  evidence, and the legal requirements against what exists.
- Law changes. The timelines in `05_LEGAL_COMPLIANCE_IMPLEMENTATION.md` are my reading of the rules; a lawyer must
  confirm them.
