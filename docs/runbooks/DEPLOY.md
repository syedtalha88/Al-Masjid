# Deploy runbook

> For the owner. How a change gets from GitHub to staging and production, how to undo it, and where secrets live.
> Background: DECISIONS #21, #27, #42, #49, #55, #57, #59. **Status (16 Oct 2026): staging is live** —
> https://app-staging.almasjids.com and https://admin-staging.almasjids.com, deployed automatically from `main`.
> Production goes live in Phase 9.

**Reaching the server:** WireGuard app → activate `masjid-server` → `ssh talha@10.66.0.1`. Public SSH is closed. If
the tunnel ever fails, the Hostinger panel's browser terminal (VNC console) always works.

## 1. How a release happens

```
push to main ──► CI (5 checks) ──► all green? ──► "Release to staging" job
                                                     builds the server + web images from that exact commit,
                                                     pushes them to GitHub's registry (GHCR) by digest,
                                                     writes a release manifest (the digests)
                                                            │
                                                     signs it with the staging key (GitHub pre-release
                                                     "staging-current")
                                                            │
             VPS (staging), every minute: fetch → verify signature → newer than what runs? → compose policy
             → rolling replacement by digest (health first, logs archived) → smoke checks
```

- **Nobody and nothing logs in to the server to deploy.** GitHub never has a key to the VPS (DECISIONS #27). The
  server fetches new releases itself.
- A release is identified by its **commit SHA** (the 40-character id GitHub shows for each commit).
- Where to see it: GitHub → **Actions** → *CI* → the run → *Release to staging* → the summary shows the manifest.

## 2. Production

1. Check the change on staging (your phones, the testing guide).
2. GitHub → **Actions** → **Deploy production** → **Run workflow** → paste the commit SHA that runs on staging.
3. GitHub asks **you** to approve (Environments → `production` → required reviewer — guide check 0.17).
4. The workflow re-uses the exact server image staging ran (same digest, never rebuilt), builds the production web
   image and writes the production manifest. The production VPS picks it up (**T0.14 / Phase 9**).

Database migrations will also need your approval in production (Phase 1 adds them).

### What is running, and why did a deploy fail?

```
sudo tail -n 3 /var/lib/masjid-connect/staging/releases.log     # deployed releases (newest last)
sudo journalctl -u mc-deploy@staging -n 40 --no-pager            # the last deploy runs (quiet = already up to date)
sudo docker ps --format '{{.Names}} | {{.Status}}'               # containers and health
sudo /usr/local/lib/masjid-connect/check.sh | grep -E "^(FAIL|WARN|==)"   # hardening check: expect 0 FAIL
```

A failing deploy keeps the old containers running and retries every minute. The journal shows the failing
container's last log lines (F33). To pause the retries while you look: `sudo systemctl stop mc-deploy@staging.timer`
(and `start` it again afterwards).

## 3. Rollback

Every deployed (signed) manifest is kept on the server and recorded in
`/var/lib/masjid-connect/<environment>/releases.log`. Rolling back = deploying an earlier manifest's digests again;
no rebuild:

```
sudo /usr/local/lib/masjid-connect/deploy.sh staging --rollback
```

Each run goes one release further back. The releases you rolled back from are skipped by the every-minute timer
until a **newer** release is published (fix → merge → CI). To return to the published release sooner:
`sudo rm /var/lib/masjid-connect/staging/rolled-back` (the timer redeploys it within a minute). Demonstrated on
staging on 16 Oct 2026 (owner check 0.14): `6bde56e` → `eae9d1c` in about a minute with the site up throughout, then
forward again automatically with the next release.

## 4. Where configuration and secrets live

| What | Where | Who can see it |
|---|---|---|
| Server secrets (database passwords, Redis passwords, session pepper, encryption keys, VAPID private key, Cloudinary keys, Cloudflare purge token, Sentry DSN for the server) | On the VPS only: `/etc/masjid-connect/<staging|production>/<process>.env`, mode 600, owner root — one file per process | Root on the server |
| Public build values (`VITE_PUBLIC_*`: API path, origins, VAPID public key, Turnstile site key, browser Sentry DSN) | GitHub → Settings → Environments → `staging` / `production` → **Variables** | Public anyway (they ship in the app) |
| Sentry upload token (optional) | GitHub → Settings → Secrets → Actions → `SENTRY_AUTH_TOKEN`; variables `SENTRY_ORG`, `SENTRY_PROJECT_WEB`, `SENTRY_PROJECT_SERVER` | Only GitHub Actions |
| Local development secrets | `.env.local*` files on a developer's PC, generated by `pnpm setup:local` | That PC only (git-ignored) |

Never paste a secret into a chat, an issue, a commit or a screenshot.

### Add or change a server secret

Connect through the WireGuard tunnel (`ssh talha@10.66.0.1`), then:

```
sudo nano /etc/masjid-connect/staging/api-admin.env     # one file per process; keeps mode 600 root
sudo /usr/local/lib/masjid-connect/deploy.sh staging --restart
```

Containers read their env file only when they are created, so `--restart` re-deploys the current release with a
rolling replacement (no downtime). The same applies after replacing a certificate in `certs/`. Never regenerate
existing keys with `make-env.sh` — `--force` keeps every value; rotating a key is a deliberate step (Claude Code
prepares it with you; FIELD_ENCRYPTION_KEY moves to FIELD_ENCRYPTION_OLD_KEYS with a new id, the VAPID key never
changes after Phase 4).

### Add or change a public build value

GitHub → Settings → Environments → `staging` (or `production`) → Variables → edit → re-run the release (push a
commit — a staging release always follows a green CI run on `main`).

## 5. Maintenance

| When | What |
|---|---|
| New host scripts / router config / systemd units (a commit Claude Code tells you about) | `curl -fsSLO …/<sha>/infra/vps/provision.sh` + sha256 check, then `sudo bash provision.sh host <sha>` — the host layer never updates itself from a release (DECISIONS #59) |
| Cloudflare e-mails "Authenticated Origin Pulls certificate expires" (30 and 14 days before; the client certificate is valid 2 years from 14 Oct 2026) | As root in `/etc/masjid-connect/aop/`: create a new key + CSR and sign it with `ca.key` exactly as in DECISIONS #57 / `infra/cloudflare/README.md` §2, upload it in **SSL/TLS → Origin Server → Authenticated Origin Pulls → Zone-level**, delete the new `leaf.key` from the server. The server side (our CA) does not change. |
| Origin CA certificate (valid until Oct 2041) | Create a new one in **SSL/TLS → Origin Server**, replace `certs/origin.pem` + `origin-key.pem` (root:1000, 640) — **including the `-----BEGIN …-----` and `-----END …-----` lines** (on 16 Oct 2026 they were missing and Caddy refused to start). Run `check.sh` (it now checks that both files parse and match), then `deploy.sh <env> --restart` |
| Production goes live (Phase 9) | Production signing key exactly like staging's (T0.14 plan step B) but with `masjid-connect-production` and the `production` environment (secret `RELEASE_SIGNING_KEY`, deployment branches = `main`, required reviewer = you); `make-env.sh production`; fill the external values it leaves empty; `systemctl enable --now mc-deploy@production.timer` |

## 6. If something goes wrong

| Situation | First action |
|---|---|
| CI is red on `main` | Nothing reaches staging — fix forward or revert the commit |
| Staging broken after a release | Roll back (section 3) |
| A deploy keeps failing ("Failed to start mc-deploy@…") | `sudo journalctl -u mc-deploy@staging -n 60 --no-pager` — the error and the failing container's log lines are there; the old version keeps running |
| Cloudflare injects scripts again (console shows `cloudflareinsights` blocked by CSP) | Cloudflare → Web analytics → the site → **Disable** automatic setup (it was found re-enabled on 16 Oct 2026) |
| Attack / traffic spike | Cloudflare → *Under Attack* mode (04 §13) |
| Suspected leaked secret | Rotate it at the source (Atlas user, Redis ACL, Cloudinary key, …), update the env file, restart — then tell Claude Code to review logs |
| Notifications must stop now | Stop the `worker` container (Phase 4 adds the "pause all push" switch) |

## 7. First Super Admin (once per environment)

The first Super Admin is created by a one-off command that prints a **one-time invite link** (72 h). Open it on your
phone and create the passkey there; then add a **second passkey** on another device (Account → Add device) so losing
one phone never locks you out (04 §3).

- **Local:** `pnpm bootstrap:super-admin --name "Your Name"` (refuses when one exists; `--force-additional` adds
  another).
- **Staging / production** (DECISIONS #70 — a one-off api-admin container; needs the host layer with this option,
  `provision.sh host <sha>` of 19 Oct 2026 or later):

  ```bash
  sudo /usr/local/lib/masjid-connect/deploy.sh staging --bootstrap-super-admin --name "Your Name" --locale en
  ```

  The link is printed once in your SSH session — never paste it into chat, e-mail or a ticket (Claude Code does not
  need it); if it leaks or expires, run the command again with `--force-additional` and disable the unused admin
  later. "A Super Admin already exists" = it ran before; nothing was changed.

## 8. One-time: internal edge networks (re-review S-L9, after the host-layer update of Oct 2026)

The edge networks between the router and each environment's `web` container became `internal` (no internet route
for `web`). Docker cannot change that on an existing network, so after `provision.sh host <sha>` run once, as root
(staging is offline for a few minutes).

**Before you start:** the newest release must already be deployed (`curl -s https://app-staging.almasjids.com/api/v1/health`
shows its version and `"db":"ok"`). The last command recreates `web` and needs a working deploy, including migrations.
Run every line, including the last two. If you stop after `network rm`, the site stays down (Cloudflare 525) until
they run.

```bash
cd /usr/local/lib/masjid-connect
docker compose -p mc-edge -f edge/docker-compose.edge.yml down          # router off
docker ps -q --filter network=mc-edge-staging | xargs -r docker stop     # web containers off the old network
docker network rm mc-edge-staging mc-edge-production
docker compose -p mc-edge -f edge/docker-compose.edge.yml up -d --wait   # router + new internal networks
docker ps -aq --filter label=com.docker.compose.project=mc-staging --filter label=com.docker.compose.service=web | xargs -r docker rm
                                                                         # the stopped web container: its old network is gone, it can never start again
./deploy.sh staging --restart                                            # a new web container on the new network; site back
./check.sh                                                               # then send Claude Code the output
```

(20 Oct 2026: without the `docker rm` line, `--restart` tries to start the old container again. Its network was
removed, so it exits with code 128 and the site stays at 525.)
