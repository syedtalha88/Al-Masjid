## Order of work

1. **Read-only look at the server** — `uname -a`, `lsb_release -a`, `ss -tuln`, `df -h`, `free -h`. Nothing changes.
2. **Review `infra/vps/provision.sh` line by line** (in the repo since 14 Oct, untested on a real server), then run
   `provision.sh base --admin <name> --admin-key "<your ssh-ed25519 public key>"`.
   It creates the admin user, hardens SSH, enables unattended upgrades + NTP, installs Docker Engine + Compose,
   WireGuard, fail2ban, ufw with Cloudflare-only 443 + the `DOCKER-USER` rule, the weekly Cloudflare-IP refresh
   timer, `/etc/masjid-connect/{staging,production}/` (600) and the log archive directory (700). It is idempotent.
3. **WireGuard:** `provision.sh wireguard`, then on each device generate a key pair and run
   `provision.sh wg-peer <name> <device public key> 10.66.0.N`; connect; SSH over the tunnel; then
   `provision.sh lockdown` (refuses unless your session already comes through the tunnel).
   **Log archive key:** on your PC run `age-keygen -o masjid-logs.key` (keep it offline); put the printed public key
   into `/etc/masjid-connect/log-archive.pub` on the server.
4. **Run `infra/vps/check.sh`** (already in the repo, read-only) — all PASS before continuing.
5. **Cloudflare:** DNS `app-staging`, `admin-staging`, `media-staging` (proxied); SSL **Full (strict)**; Origin CA
   certificate (15 years) → `/etc/masjid-connect/staging/certs/` (600); **Authenticated Origin Pulls** on; Rocket
   Loader / Email Obfuscation / auto-injected analytics **off**; cache rules + WAF baseline documented in
   `infra/cloudflare/`.
6. **Env files:** you fill each process's secrets on the server (`api-public.env`, `api-admin.env`, `worker.env`) —
   Claude Code lists the variable names from `.env.example`; you paste values only on the server.
7. **Release signing (DECISIONS #55):** create the staging signing key **on the server**; the public key stays in
   `/etc/masjid-connect/staging/allowed_signers`; the private key goes into GitHub → Environments → `staging` →
   secret `RELEASE_SIGNING_KEY`, then is deleted from the server. (Production gets its own key later.)
8. **Deploy timer** (DECISIONS #56): `systemctl enable --now mc-deploy@staging.timer` (root; installed by
   `provision.sh base`); first deploy; smoke + header checks; securityheaders.com and Mozilla Observatory **A+** (guide 0.2).
9. **Rollback demo** (guide 0.14), **origin lock-down test** (direct IP refused — guide 0.13), latency to Atlas
   ap-south-1 measured for the report. Then **reboot once** and re-run `check.sh`: the ipsets and the DOCKER-USER
   rule must come back (`mc-docker-user-firewall.service`, after Docker), the edge + staging stacks restart on their
   own, and `systemctl list-timers 'mc-*'` shows all timers. (Between Docker starting and that unit, 443 is briefly
   reachable from any IP; Authenticated Origin Pulls still refuse non-Cloudflare TLS clients in that window.)
10. Your phone checks from the testing guide (0.1–0.12), including the iPhone swipe-back question (F17).

## Topology on the one VPS (DECISIONS #42, #54)

```
Cloudflare ──443 (only Cloudflare IPs: ufw + DOCKER-USER)──► mc-edge: HAProxy, TCP mode, routes by SNI
                                                               │  app-staging./admin-staging./media-staging. ─► mc-staging web (Caddy, TLS + client cert)
                                                               │  app./admin./media.                         ─► mc-production web (Caddy, TLS + client cert)
                                                               └  anything else → connection closed
mc-staging:    web · api-public ×2 · api-admin ×2 · worker · redis      (own network, own env dir, own Redis ACL)
mc-production: same, separate everything (started in Phase 9)
```
- The edge router never decrypts: each environment's Caddy terminates TLS with its own Origin CA certificate and
  verifies Cloudflare's client certificate (Authenticated Origin Pulls), exactly as the Caddyfile does today
  (`CADDY_TLS=origin`). The router holds no keys.
- No port 80 on the server: Cloudflare's "Always Use HTTPS" redirects; Cloudflare connects to the origin on 443 only.
- Client IPs for rate limits still come from `CF-Connecting-IP` (`TRUSTED_PROXY_MODE=cloudflare`).

## Release delivery (DECISIONS #27, #55, PROGRESS F25)

```
CI (main, green) → Release to staging: images → GHCR (digests) → release-manifest.json
                 → signed with the staging key (ssh-keygen -Y sign, namespace masjid-connect-release)
                 → uploaded to the GitHub pre-release "staging-current" (manifest + .sig, replaced each time)
VPS deploy timer (every minute, user deploy): curl the two files → ssh-keygen -Y verify against allowed_signers
                 → new release? → docker compose pull by digest → migrate (later) → rolling restart with
                   health waits → smoke checks → append to deploy/releases.log (rollback = previous line)
```
No credential that can reach the VPS exists in GitHub; a stolen GitHub token can at most publish a manifest that
the server rejects unless it carries a valid signature from the environment's key.
